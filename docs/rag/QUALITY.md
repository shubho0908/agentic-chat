# RAG quality and evaluation

The production ranking path uses semantic retrieval plus PostgreSQL lexical retrieval, RRF fusion, and Cohere reranking. Query rewrites are fused with RRF instead of short-circuiting. `RAG_LEXICAL_LANGUAGE` selects PostgreSQL's text-search configuration and defaults to `english`.

`npm run eval:rag` reports Recall@K, MRR, and nDCG@10 from a labeled JSON fixture. The checked-in fixture is a deterministic harness smoke test, not a production-quality claim. Add representative queries and stable chunk IDs from the application's document domains before setting release thresholds.

Citation match percentages come only from bounded scores: semantic cosine similarity or a reranker relevance score. Raw lexical `ts_rank_cd` values order fusion but are never displayed as percentages; a citation whose only evidence is lexical shows no percentage rather than a clamped "100% match".

The Jev passage gate is a separate post-rerank seam. `JEV_PASSAGE_GATE_MODE=shadow` records relevance, usable-evidence, contradiction, and prompt-injection decisions without filtering. `active` filters confident failures, fails open on provider errors. Evaluations fan out with bounded concurrency (4 in flight, like the Jev reranker); the first failure aborts the remaining batch and the gate fails open rather than bursting requests at a degraded provider. If all passages are rejected, retrieval returns no evidence rather than reintroducing unsafe passages. Default is `off`. Store `TYPESAFE_API_KEY` only in deployment secrets.

The Jev cache gate sits on the semantic-cache serve path (both the client pre-check server action and the orchestrator short-circuit). `JEV_CACHE_GATE_MODE=shadow` records serve/veto verdicts without changing behavior; `active` vetoes on a single confident signal - low serve-confidence or high staleness risk - because a false veto costs one fresh generation while a false serve hands the user a stale answer, and it fails open on provider errors so an outage can never turn hits into misses. In active mode the client pre-check defers to the orchestrator so each entry is evaluated exactly once; shadow/ab keep the pre-check fast path because they never change behavior. Only structural signals (similarity score, margin over threshold, entry age vs TTL, conversation scoping, query/answer lengths) are evaluated - cached question and answer content never leaves for the evaluation API.

The Jev HITL escalation checkpoint (`JEV_HITL_ESCALATION_MODE`) compares Jev's review verdict against the deterministic dangerous-action blocklist in the tool node. Shadow/ab log agree/disagree outcomes only. Active can add a human-approval interrupt for calls the blocklist missed (confident review verdict plus irreversible/external effect risk), but can never suppress a deterministic escalation; the verdict rides in graph state keyed by a hash of the tool-call set so an interrupt resume replays the identical branch. Tool arguments reach the evaluation API as type-only previews, never user content.

Every decision record from every checkpoint is also persisted to the `jev_decisions` table (redacted metadata only - no user content, no raw state), so shadow-mode evidence is queryable instead of buried in logs. `GET /api/jev/stats?days=30&checkpoint=planner` returns a per-checkpoint report over a sliding window (default 30 days, max 90): outcome breakdown (agree/disagree and gate verdicts), fallback rate, and p50/p95 latency. The endpoint is read-only and owner-only: the signed-in email must match `JEV_STATS_ALLOWED_EMAIL`, and an unset or blank value denies everyone (403).
